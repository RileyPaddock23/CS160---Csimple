# Csimple Compiler Architecture

This document describes the internal design of the Csimple compiler front-end.

---

## High-Level Overview

The compiler is organized as a classic front-end pipeline:

```
Source Text
    │
    ▼  lexer.l (Flex)
Tokens
    │
    ▼  parser.ypp (Bison)
Parse Tree / AST
    │
    ▼  typecheck.cpp (Visitor)
Annotated AST  ──── errors → stderr
    │
    ▼  ast2dot.cpp (Visitor)
GraphViz DOT  ──────────────→ stdout
```

Each phase is implemented in its own file and communicates through the AST data structure.

---

## Source Files

| File               | Role                                                              |
|--------------------|-------------------------------------------------------------------|
| `lexer.l`          | Flex grammar — tokenizes the input stream                         |
| `parser.ypp`       | Bison LALR(1) grammar — builds the AST during parsing             |
| `ast.cdef`         | Domain-specific language describing the AST node hierarchy        |
| `astbuilder.gawk`  | AWK script that generates `ast.cpp` and `ast.hpp` from `ast.cdef` |
| `ast.cpp/ast.hpp`  | Auto-generated AST node classes (do not edit by hand)             |
| `attribute.hpp`    | `Attribute` struct — carries type and scope annotations           |
| `primitive.hpp/cpp`| Wrappers for integer and string literal values                    |
| `symtab.hpp/cpp`   | Symbol table with nested-scope support                            |
| `typecheck.cpp`    | Semantic analysis visitor (type checker)                          |
| `ast2dot.cpp`      | AST → GraphViz DOT visualization visitor                         |
| `main.cpp`         | Entry point — wires the pipeline together                         |

---

## Phase 1: Lexical Analysis (`lexer.l`)

The lexer is written in **Flex** and tokenizes the source into terminals consumed by the parser.

Key details:
- Line tracking is done automatically with `%option yylineno`.
- Comments (`/% ... %/`) are handled with an exclusive start condition.
- Integer literals are parsed in four bases: decimal, hexadecimal (`0x…`), octal (`0…`), and binary (`…b`).
- Character literals use single quotes (`'a'`); string literals use double quotes.
- Identifiers start with a letter and may contain letters, digits, and underscores.
- Any unrecognized character calls `yyerror()` and terminates parsing.

---

## Phase 2: Syntax Analysis (`parser.ypp`)

The parser is written in **Bison** and implements an LALR(1) grammar for Csimple.

Key grammar rules:

| Rule                     | Description                                         |
|--------------------------|-----------------------------------------------------|
| `Program`                | Top-level: list of procedures                       |
| `procedure_declaration`  | Procedure with parameter list, return type, body    |
| `procedure_block`        | Body: nested procs, variable decls, statements, return |
| `statement`              | Assignment, call, if, while, or code block          |
| `expression`             | Full expression hierarchy (see precedence table)    |
| `type`                   | All supported types including `string[N]`           |

The parser builds AST node objects (allocated on the heap) and attaches them as Bison `$$ = ...` semantic values. The root node (`Program_ptr ast`) is a global variable accessed by `main.cpp`.

---

## Phase 3: AST Code Generation (`ast.cdef` + `astbuilder.gawk`)

Rather than writing the many AST node classes by hand, the project uses a **code-generation approach**:

1. `ast.cdef` declares the AST grammar in a compact DSL:
   ```
   Stat:IfWithElse ==> Expr Nested_block Nested_block
   ```
   This means `IfWithElse` is a subclass of `Stat` with three children: an `Expr` and two `Nested_block` nodes.

2. `astbuilder.gawk` reads `ast.cdef` and emits ~1,400 lines of C++ implementing:
   - Concrete `*Impl` classes for every node type
   - A `Visitor` abstract base class with a `visit_*()` method per node
   - `accept(Visitor*)` dispatch on every node
   - `clone()` methods

This approach means adding a new AST node requires only one line in `ast.cdef`; the C++ boilerplate is generated automatically by running `make ast`.

### Node Conventions

- A `*` prefix in the cdef file (e.g., `*Proc`) means the field is a `std::list<Proc_ptr>`.
- Leaf types (`SymName`, `Primitive`, `StringPrimitive`) are marked `external` and implemented manually.

## Phase 4: Semantic Analysis (`typecheck.cpp`)

The type checker is implemented as a **Visitor** that walks the AST in post-order (children before parents).

### Visitor Pattern

```
Abstract base: Visitor (generated by astbuilder.gawk)
    │
    └─ Typecheck : public Visitor   ← typecheck.cpp
    └─ Ast2dot   : public Visitor   ← ast2dot.cpp
```

Every AST node implements `accept(Visitor* v)`, which calls the appropriate `v->visit_*()` method. This decouples tree traversal logic from the node classes themselves.

### Symbol Table (`symtab.hpp/cpp`)

The symbol table uses a **tree of scopes**:

```
SymTab
  └─ SymScope (global scope)
       ├─ Symbol "Main"  (procedure)
       └─ SymScope (Main's scope)
            ├─ Symbol "x"  (integer variable)
            └─ Symbol "p"  (intptr variable)
```

Key operations:

| Method                  | Description                               |
|-------------------------|-------------------------------------------|
| `open_scope()`          | Push a new scope (entering a procedure)   |
| `close_scope()`         | Pop the current scope (leaving a procedure) |
| `insert(name, symbol)`  | Add a symbol to the current scope         |
| `lookup(name)`          | Search current and enclosing scopes       |
| `exists(name)`          | Check only the current scope (for dup detection) |

### Type Attributes (`attribute.hpp`)

Each AST node carries an `Attribute` that records:
- `m_basetype` — the `Basetype` enum value (`bt_integer`, `bt_boolean`, etc.)
- `m_scope` — pointer to the scope where the node was defined
- `lineno` — source line number for error messages
- `m_place` — register index placeholder for a future code-generation phase

### Type Checking Logic

The type checker performs the following checks:

| Check                       | Description                                              |
|-----------------------------|----------------------------------------------------------|
| Main procedure existence    | Exactly one procedure named `Main` must exist            |
| Main has no parameters      | `Main` must be declared with an empty parameter list     |
| Duplicate procedure names   | Two procs with the same name in the same scope           |
| Duplicate variable names    | Two variables with the same name in the same scope       |
| Undefined procedure call    | Calling a procedure that has not been declared           |
| Undefined variable use      | Reading/writing a variable that has not been declared    |
| Argument count mismatch     | Wrong number of arguments in a procedure call            |
| Argument type mismatch      | Argument types do not match parameter types              |
| Return type mismatch        | Returned expression type differs from declared return type |
| If/while predicate type     | Predicate expression must be `boolean`                   |
| Array index type            | Array index must be `integer`                            |
| Non-array indexing          | Indexing a variable that is not `string`                 |
| Assignment type mismatch    | Left-hand side and right-hand side types must match      |
| Incompatible expression     | Operands of incompatible types in binary expressions     |
| Pointer arithmetic          | Arithmetic on pointer types is not allowed               |
| Absolute value type         | `|x|` requires an `integer` operand                     |
| Address-of restrictions     | `&` applied to an invalid target                         |
| Invalid dereference         | `^` applied to a non-pointer type                        |

## Phase 5: AST Visualization (`ast2dot.cpp`)

`Ast2dot` is another `Visitor` that traverses the annotated AST and emits GraphViz DOT syntax. Each node is assigned a unique integer ID; directed edges represent parent-child relationships.

Pipe the output to `dot` to produce a rendered image:

```bash
./csimple < prog.csimple | dot -Tpng -o ast.png
```

---

## Entry Point (`main.cpp`)

`main.cpp` is intentionally minimal:

1. Calls `yyparse()` — runs the lexer/parser to build the AST.
2. Creates a `SymTab` and a `Typecheck` visitor, then calls `ast->accept(typechecker)`.
3. Creates an `Ast2dot` visitor and calls `ast->accept(ast2dot)` to emit DOT output.

## Build System (`Makefile`)

| Target      | Action                                                    |
|-------------|-----------------------------------------------------------|
| `make`      | Build the `csimple` executable                            |
| `make ast`  | Regenerate `ast.cpp` and `ast.hpp` from `ast.cdef`        |
| `make clean`| Remove object files, executable, and generated C++ sources|
| `make veryclean` | Same as `clean`, plus removes `ast.cpp` and `ast.hpp` |

The Makefile uses standard implicit rules for `.l → .cpp` (Flex) and `.ypp → .cpp` (Bison), then compiles all `.cpp` files to object files and links them.
